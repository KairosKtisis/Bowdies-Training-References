a guest without scrambling.

## Known gaps (Phase 9+ workstreams)

### Gap 1 — ELEGANT_RED and default-path bottles have no per-bottle variants
**Severity:** Medium
**Why:** BOTTLE_PROFILES_CURATED contains only 62 of the 491 entities. The rest
(Pinots, Burgundy, most Bordeaux, the broader sparkling/white-wine list, etc.) flow
through the generator's default profile path. Their templated notes still draw from
the expanded WORKS connective pool (Session 18) but do not have bottle-specific
bridge1/bridge2 variants.
**Fix path:** Build a category-level variant mechanism — `class_bridge_variants.js`
keyed by drinkClass, with 4-6 variants per class. Generator falls through from
bottle-specific → class-level → original. Estimated 2-3 sessions of work for the
remaining 8 classes (ELEGANT_RED, COGNAC, SPARKLING, WHITE_WINE, GIN, VODKA,
APERITIVO_BITTER, SWEET_LIQUEUR).
**Recommendation:** Open as Phase 9 after a quality-rest gap. Not blocking floor
deployment.

### Gap 2 — Templated count dropped to ~33 (good) but those 33 should be audited
**Severity:** Low
**Why:** After Phase 7 + regen, the templated detector classifies only ~33 of 51,242
notes as "still templated". These are the ones the engine could not lift into
character-specific phrasing — likely because the bottle's class fell into a default
bucket. Worth a one-pass review to confirm they're acceptable.
**Fix path:** Add a `audit_remaining_templated.js` script that prints the 33 notes
with their entity classes, surface the pattern, and decide on case-by-case lifts.

### Gap 3 — Raventós Cava de NIT has NULL drink class
**Severity:** Low
**Why:** The drinkClassFor() function returns null for Raventós Cava de NIT Rose
Brut. Variants were written and merged but the templated path may not be picking it
up correctly.
**Fix path:** Add explicit override `'Raventós Cava de NIT Rose Brut': 'SPARKLING'`
in DRINK_CLASS_OVERRIDES (pairing_engine_taxonomy.js). One-line fix, run health
check, done. Should be picked up in Session 24.

### Gap 4 — engine_health_check.js shows ~25,588 "editorial" count, but the corpus has 51,242 keys
**Severity:** Investigation only
**Why:** Likely the health check is counting unique pairs (51,242 / 2 ≈ 25,621),
accounting for both A|B and B|A. Worth confirming the math.
**Fix path:** Read the health check source, document the counting convention, and
update the AUDIT note if it's just terminology.

## Conventions locked in

### File-write protocol (mandatory for all future sessions)
1. Write modified files to `/sessions/<session-id>/mnt/outputs/` (sandbox)
2. `cp sandbox/file engine/file` (atomic kernel-level copy)
3. Never write directly to `pairing-notes.js` via Write tool (truncation risk)
4. Back up before any modification: `cp pairing-notes.js pairing-notes.js.pre-<sN>.bak`

### Canonical-sorted-key hash for any pair-keyed sweep
- Use `[a, b].sort().join('|')` as the hash seed
- Prevents mirror desync — both A|B and B|A resolve to the same variant pick
- Applied successfully in S19, S20, S21, S22 (0 desync × 4 sessions in a row)

### Pre-commit factual scans
- Cooking-method drift (steaks must be flame-grilled, not seared/pan-seared)
- Dessert ingredient canon (carrot cake = cream cheese + cinnamon, no raisins/nuts)
- Steak weight canon (10/14/18/26/36/40 oz; never invent)

### Audit-then-lift discipline
- Don't rewrite already-strong editorial
- Each session pre-audits before scoping variant volume
- Surface scope reality to user when expectations exceed reality (S20 surfaced
  6 Cabs vs ~15 expected; S22 surfaced 218 templated vs hypothetical "many")
